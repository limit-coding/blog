## Go 语言从哪来

Go 由 Google 的 Robert Griesemer、Rob Pike、Ken Thompson 于 2007 年设计，2009 年开源，2012 年发布 1.0，承诺向后兼容。设计目标很直接：解决 C++ 编译慢、依赖复杂，以及当时脚本语言在大规模并发服务上表现不足的问题——本质上是"给 Google 内部大规模分布式系统写的语言"。

关键节点：

* 2009：开源，语法定型（简洁、强制 `gofmt`）
* 2012：Go 1.0
* 2015–2017：Docker、Kubernetes、etcd 等基础设施项目采用 Go，奠定其"云原生语言"地位
* 2018：Go Modules 引入，解决依赖管理痛点
* 2022：Go 1.18 引入泛型

**与 Python 对比**：Python 动态类型、解释执行（CPython 有 GIL，真正并行只能靠多进程），生态偏数据科学/胶水脚本，开发快但运行时性能弱，大并发场景需要 asyncio 或额外框架支撑。Go 静态类型、编译为原生二进制，goroutine + channel 是语言一等公民，不需要额外框架就能写高吞吐服务，性能通常比 Python 高一到两个数量级，代价是类型系统更严格。

**与 C++ 对比**：C++ 手动内存管理、模板元编程能力强，理论性能上限更高，但编译慢、心智负担重。Go 用 GC 自动管理内存，刻意精简语法（没有继承、没有异常、没有复杂泛型元编程），编译速度极快，代价是牺牲部分极致性能，换来工程团队的协作效率和可维护性。

一句话总结：Python 换开发效率，C++ 换运行时性能上限，Go 换的是"工程团队大规模协作 + 并发服务开发效率"的平衡点——这也是它成为 K8s、Docker、大量微服务网关首选语言的原因。

## 并发模型的三种做法

Go 需要在少量 OS 线程上调度海量 goroutine，业界有三种做法：

| 模型 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| N:1 | 用户态线程全部映射到一个内核线程 | 并发切换成本低 | 无法利用多核，一个阻塞全部卡死 |
| 1:1 | 每个协程对应一个内核线程（早期 Java 类似） | 能利用多核 | 内核态切换成本高（几百 KB 栈），几万并发就撑不住 |
| M:N | M 个 goroutine 跑在 N 个内核线程上，复用调度 | 栈可从 2KB 动态增长，创建成本极低 | 调度器实现复杂 |

GMP 就是 Go 对 M:N 模型的具体实现。

## GMP 三要素

* **G（Goroutine）**：一次运行现场，包含程序计数器状态：runnable / running / waiting / dead。不是线程，是一个轻量级结构体，初始栈只占 2KB，按需通过扩容翻倍。
* **M（Machine）**：真正的 OS 线程（对应 pthread 或 clone 出的内核线程）。M 本身不能直接执行 Go 代码，必须绑定一个 P 才能从其本地队列取 goroutine 来跑。数量默认上限一万（`runtime.SetMaxThreads` 可调），但真正活跃跑代码的 M 数受 P 数量制约。
* **P（Processor）**：调度的核心抽象，是执行 Go 代码所需资源的"许可证"。数量由 `GOMAXPROCS` 决定，默认等于 CPU 核数。每个 P 持有一个本地可运行队列（容量 256）和内存分配的本地缓存（减少全局锁竞争）。

必须 M 绑定 P 才能执行 G，所以真正并行执行 Go 代码的并发度上限就是 `GOMAXPROCS`。这也是为什么"一个 Agent 会话一个 goroutine"这种模型能在 Go 后端里轻松跑到几十万并发——创建成本极低，调度完全在用户态完成。
