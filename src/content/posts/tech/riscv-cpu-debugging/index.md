自己搭一个简化 CPU 时，最折磨人的现象不是完全不运行，而是“前几条指令都对，随后突然跑飞”。如果只盯着最终寄存器值，很难判断错误从哪里开始扩散。

我后来采用的原则是：**不要解释最后一个错误，要找到第一个错误周期。**

## 先建立可观察轨迹

每个周期至少记录：

```text
PC | instruction | rs1 | rs2 | immediate | ALU result
memory address/data | write-back register/data | branch decision
```

然后拿一段很短的程序手工推演，逐周期对比。第一个与预期不一致的字段，往往比模拟器最后的报错更接近根因。

## 按数据通路反向定位

例如写回值错误，我不会立刻检查整个 ALU，而会顺着路径倒推：

1. 写回多路选择器选的是 ALU、内存还是 PC？
2. 寄存器写使能是否在正确周期拉高？
3. 目标寄存器编号是否来自正确字段？
4. 上游计算结果是否已经错误？

这样每一步只验证一个局部契约。

## 最常见的是边界问题

我遇到最多的错误并不神秘：立即数拼接顺序、符号扩展、移位后补零、比较时的有符号性、地址低位处理，以及控制信号默认值。

尤其要显式写清位宽。例如分支偏移并不是“把几个字段连起来”就结束了，还需要确认符号位、隐含的低位零和与 PC 相加时的宽度。

## 为控制器准备真值表

不要让控制逻辑散落在多个组件里。可以把 opcode、funct 字段映射为一张控制表，再检查每条指令对应的：

- ALU 操作；
- 操作数来源；
- 内存读写；
- 写回来源；
- PC 更新方式。

新增指令时先补表，再改电路，能减少“修好一种指令、破坏另一种”的回归。

最后，我会把每次错误压缩成一个最小测试，并保留到回归用例里。硬件调试和软件调试一样：可观察、可复现、从第一个偏差开始，复杂系统才会逐渐变得可解释。
