课程资料并不稀缺，真正困难的是判断先学什么、依赖什么，以及一个资源为什么值得信任。我设计学习路线平台时，把核心对象从“文章列表”改成了**可验证的知识节点与依赖关系**。

## 最小数据模型

平台至少需要四类对象：

- `Topic`：知识节点，包含目标、先修要求和掌握标准；
- `Edge`：节点之间的先修、并列或扩展关系；
- `Resource`：课程、教材、实验或文章，关联适用节点；
- `Review`：资源来源、审核意见、版本与状态变化。

图数据库不是必需条件。早期可用关系数据库保存节点和边，通过递归查询生成路线；当图查询和关系分析真正成为瓶颈时，再引入专门图存储。

## 投稿与审核流水线

任何人都可以提交公开、获授权的学习资源，但不能直接进入正式路线：

```text
资源提交 → 格式校验 → AI 预审 → 人工审核 → 发布 → 反馈与修订
```

AI 预审负责提取主题、预测先修要求、检查重复项并生成审核摘要。它不负责最终判断内容是否正确。审核者需要看到原始来源、模型依据和可能冲突，所有状态变化都保留记录。

## 个性化不是随意推荐

用户先完成自评或小测，得到“已掌握、待验证、未学习”的节点集合。路线生成器从目标节点反向遍历先修关系，再根据可用时间和资源偏好排序。

向量检索适合寻找语义相近资源，不能替代明确的先修边。一个内容“看起来相关”，不代表它处在正确学习顺序里。

## 权限与边界

管理员、审核者、贡献者和普通学习者应有不同权限。平台只索引公开或获授权内容，不把受限课程、个人作业和登录后数据当作默认数据源。删除请求也应沿关联关系清理缓存和检索索引。

## 从单体开始

第一版可以由一个 API 服务、关系数据库、后台任务队列和前端图组件组成。模型调用放在异步任务中，输出必须通过固定 schema；审核和发布路径保持确定性。等到检索、审核或计算路线出现独立扩缩容需求，再拆服务。

这个设计最重要的不是使用哪套框架，而是把“路线为什么这样安排”公开出来。学习平台不应替用户制造更多信息，而应帮助用户看见知识结构、证据来源和下一步行动。
