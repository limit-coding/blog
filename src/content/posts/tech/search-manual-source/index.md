遇到技术问题时，我以前容易在两个极端之间摇摆：要么不断更换关键词，希望搜到一条完全相同的答案；要么一开始就钻进源码，结果很快迷路。更有效的办法，是把排错看成一条逐层加深的阶梯。

## 第一层：把现象写准确

不要只搜“不能运行”，而要先记录：

- 输入、预期输出和实际输出分别是什么；
- 最小复现需要哪些步骤；
- 软件版本、运行环境和完整错误信息；
- 最近一次正常运行与当前状态之间改了什么。

好的问题描述本身就完成了一半定位。搜索词也应该包含稳定特征，例如错误码、核心函数名和最小环境，而不是整段自然语言猜测。

## 第二层：先查一手文档

搜索引擎适合发现入口，官方手册负责定义行为。参数默认值、版本差异、生命周期和边界条件，应尽量回到官方文档或协议规范确认。

我会特别区分三类内容：

1. 文档明确保证的行为；
2. 社区经验总结出的常见表现；
3. 只在某个版本或某台机器上出现的偶然现象。

把后两类误当成第一类，是很多“复制后暂时有效”问题的来源。

## 第三层：沿调用路径读源码

源码阅读也不应从目录第一页开始。我会以日志、堆栈或公开接口为入口，沿调用路径追踪：参数在哪里校验、状态在哪里写入、错误在哪一层被转换。

读到关键分支后，先写下自己的机制假设，再继续找证据。这样源码不是无边界的阅读材料，而是用来验证假设的地图。

## 第四层：设计最小实验

一个好的实验只改变一个变量，并能区分至少两个解释。例如怀疑缓存时，不是“清空一切再试”，而是分别改变缓存键、过期时间和进程生命周期，观察哪个操作真正改变结果。

最终记录的不应只是“运行这个命令就好了”，而应包括：

```text
现象 → 假设 → 实验 → 证据 → 根因 → 修复 → 回归检查
```

搜索能提供候选答案，手册给出契约，源码揭示实现，实验负责判定。四层配合起来，排错才从运气变成一种可以复用的能力。
