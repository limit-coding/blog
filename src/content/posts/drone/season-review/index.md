## 写在前面

我们做的这台无人机是四旋翼。因为各种原因，无人机在北京受到的抵制比较厉害，所以今年的微型无人机比赛就结束了。

客观来说，我加入无人机队是为了提升大工程的协同能力，以及落地做跟机器人相关的工作——从这个目的来说，还是达到了。

下面按 **技术路线 → 困难与踩坑 → 心得与方法论 → 给后来人的建议** 来写。

---

## 一、技术路线

整机是「开源飞控 + RDK X5 机载电脑 + Livox MID-360 激光雷达 + 前向 USB 摄像头 + 光流/激光测距定高 + 舵机投放」。机载这一侧分三条线：

**1. 雷达定位链路（室内无 GNSS 的核心）**

```
MID360 → /livox/lidar → mid360_xy_node（点云格式转换）
       → FAST-LIO → /Odometry
       → relative_pose_node（相对定位 + 安全保护）
       → /relative_pose + /localization_valid
       → fc_bridge_node → 串口 /dev/ttyFC（20Hz）→ 飞控 PID
```

- `relative_pose_node` 把**开机后的第一帧正常里程计当作原点**，默认机头方向为 +X，这样起飞定位就是 (0,0)、东南西北也有了直觉基准，现场改方向直接 `ros2 param set`，不用重编译。
- 定位不可信（NaN、跳变、离谱初值、断流）时，`fc_bridge_node` **发 0cm 心跳帧而不是真实坐标**——宁可让飞机停住，也不让坏坐标把飞机带飞。

**2. 视觉与任务决策**

二维码识别取任务（要认哪个图片靶、降落侧）→ 摄像头对图片靶做**四选一**匹配（从场上几个已知候选靶里选出与任务匹配的那个）→ 命中后触发舵机投放。模型走 `pt → ONNX → RDK .bin` 部署。

**3. 电脑 ↔ 飞控串口协议**

自定义二进制帧（`AA FF [类型] [长度] [数据] [校验]`）：电脑发位置帧 / 任务状态帧，飞控回发高度、解锁、识别触发与投放命令。

## 二、困难与踩坑

### 1. 硬件与板子

一开始用旧的 RDK X5 板子，存在短路和容易发烫的问题，后来甚至因短路起火烧坏了网卡。换成同款的新型号板子后，就没再出现这类问题。

> **心得：有时候硬件最好的办法就是换一个新的，而不是为了省钱在二手或旧硬件上不停折腾。**

### 2. 雷达定位漂移（最核心的难点）

雷达从始至终一直存在飘的问题。

- **前期同步**：要完成雷达与机载电脑的同步，配置静态 IP 等参数。
- **两种定位来源**：一种是点云，一种是 IMU（惯性单元）。在 FAST-LIO 源码的配置里可以调两者的权重：
  1. 增加 IMU 权重：更灵活，但更容易漂移；
  2. 增加点云权重：更稳定，但会有延迟。
- **时间戳问题**：不一定是问题，但当距离漂移特别离谱（比如漂几十万米）时，要先排查是不是时间戳导致的。
- **与飞控的协调最难**：很多时候发现不是雷达的问题，而是飞控接触有问题。另外雷达不是每次都稳，**开机后最好放一段时间、等定位稳了再起飞**，飞行状态会好很多。

> 起飞定位归零、东南西北、航向角这类参数，可以用 AI 辅助编写，或用类似脚手架实现（对应上面的 `relative_pose_node`）。

### 3. 网络与开发环境

- 尽量用 **SSH 连接，别用远程桌面**——远程桌面占 CPU/内存多，还容易让设备发热。
- 单独用电脑开发、脱离上机时，**尽量连网线**，无线不如网线稳，比频繁因热点断开重连好得多。
- **机载电脑只负责计算，不负责联网**：不配科学上网、不强制联网（仅用于配对）、文件先在本地下好再用 SCP 传上去，不在机载电脑端直接联网下载。所以前期用网线格外重要。

### 4. 视觉与模型

- **BPU 加速意义不大**：RDK X5 虽然标称有 BPU，但用它要做模型量化、精度会掉。实测同一个模型，CPU 上虽然稍慢但准确率更高，BPU 上速度略快、精度下降却到了无法容忍的程度。**建议直接用 CPU 跑模型。**
- **训练建议**：租一张 4090 训，本地环境容易出问题又慢——10 分钟能训完就比 1 小时强得多，因为 10 分钟训不好还能调完再训，1 小时训不好就来不及了。这是个比较经典的任务，难度不大；**不用在本地场地拍照采数据、不用新建数据集，直接用官方 CIFAR-100 即可。**
- **误识别的解法（四选一）**：识别本质就是**四选一**——不是让模型开集乱认，而是从场上那几个已知图片靶里选出跟任务匹配的那个。训练完直接认效果不一定理想，所以我先把这一轮要认的目标放进一个队列；因为视觉识别是概率性的，只要**概率排前几的结果里出现了待认目标，就直接取它**。这样能挡掉把场地里的草、云等背景误识别的情况，明显提升准确率。（再配合多帧确认，同一标签连续若干帧才发布，进一步防抖。）

### 5. 内耗

调试过程里繁琐、内耗的环节不少，比如网络、硬件芯片这些。**这种事能尽快解决就尽快解决，没必要耗着。**

## 三、心得与方法论

### 稳定性大于一切

我一直坚守的原则是：**尽量少改动，稳定性大于一切。**

每次上新功能都要先测好，不搞空中楼阁。一次改太多、传上去全是坏的，Bug 叠 Bug 就麻烦了。正确的做法是在之前好的基础上，每次只加一点点，加上去看一眼——行就继续，不行就退回来。这个习惯给了这个项目特别好的锻炼。

### 通信一定要做闭环（握手 + 回执）

通信层有很多双向信号：飞控要发信号给电脑，电脑也要发信号给飞控。**必须保证另一侧收到信号后回一个验证码**，不能只管发、不管对面到底收没收到。

举个例子：飞控发一个带数字的信号到电脑，电脑收到后要把**同样的数字发回飞控**，等于告诉它"我收到你的信息了"。

为什么这条很关键——串口是会丢字节的，单向发一次，发送方根本不知道对面收没收到。没有回执，一旦某条命令丢了，飞控和电脑的任务状态就悄悄错位了，后面全乱；有了回执才能确认、必要时重发。**双向通信一律按"发送 → 对方回执确认"来设计，别做只发不认的单向链路。**

### 怎么用好 AI 编程

- **你要对整条链路有把握**：做好链路的选取和观察，细节交给 AI，它能处理得比较好。
- **终端自己看**：观察时要开好多个终端，别让 AI 来看终端（网络不好会很卡）。你自己看，让 AI 给你写规则，你参考规则再写个差不多的。你要清楚每个终端正常输出什么、异常时输出什么，然后把这些跟 AI 讲清楚。
- **把 AI 当队友，不是纯工具**：你怎么对待队友，就怎么对待 AI；也别把它想得特别万能。查源码、调研方案和原理时让它辅助阅读，别完全靠自己搜，也别完全不看，保持平衡、多迭代试错。
- **三个工具的对比**：
  1. **Kimi Code**：比较花哨，体验没特别惊艳，而且感觉调用 token 太多——当时部署在机载电脑里，它 token 调用量太大，把内核给我烧坏了。
  2. **CodeX**：能力较强，但有时"天马行空"，让它做 A、B、C，可能给你做出 D、E、F。
  3. **Claude Code**：表现更好，让它做 A、B、C 就能准确完成，返工少。

后来我转向 Claude Code，主要就是因为返工更少。

### 硬件是另一回事

我之前主要做软件和 AI，无人机这种硬件的东西复杂得多：反馈机制、危险性、还必须跟飞控联调，内耗的地方也多。这些都挺锻炼人，也确实需要经验。

## 四、给后来人 / 队伍的建议

### 采购

1. **基本工具一定配齐，工具上别省。**
2. 硬件摸着烫手、或偶尔关机等异常，**建议直接换新**——虽然现在涨价明显，但换新往往更快解决问题。
3. 多用淘宝采购，电子类选择多、也便于报销。
4. **雷达报销要留意**：雷达贵，重报要重新开单、开单本身还要额外花钱，且单张金额要求小于 1000 元，所以开单前想好单张金额，否则重开很麻烦。

### 队伍可以改进的部分

- **代码统一进版本库**：之前不少代码只存在板子上、靠 SCP 散着传，版本容易漂也没法回溯。应该全部 git 管理 + 规范 `.gitignore`，GitHub的操作和管理不完全好，3个人一起协同比较麻烦，要有好的GitHub上传规范吧
- **协议 / 文档要有唯一权威来源**：串口协议改了要两端同步，别分散在几个文件里，可以把所有相关文件整理到一个git仓库里面方便看和整理。
- **早点固定"训练 / 部署 / 飞控"三方的接口**，并定期集成联调，别等功能都写完才第一次合。
