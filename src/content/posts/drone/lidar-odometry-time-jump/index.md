一次雷达里程计测试中，系统刚启动时轨迹正常，随后位置突然跳出极大值。直觉上我先怀疑点云退化、IMU 噪声或外参错误，但日志里有一个更反常的线索：相邻消息的时间戳发生了巨大跳变。

## 根因不在点云

嵌入式设备开机时没有可靠实时时钟，系统先使用一个明显无效的日期。网络建立后，时间同步服务把墙上时钟校正到真实时间。对于依赖时间差积分的里程计，这不是普通延迟，而是一次巨大的时间跃迁。

许多融合算法默认时间戳单调并且相邻。若用错误的 `dt` 积分速度、做点云去畸变或匹配 IMU 队列，后果会迅速扩散到整个状态估计。

## 仅配置启动顺序不够

我一开始只让里程计服务排在网络服务之后，但“网络已启动”不等于“时间已经可信”。即使时间同步服务进程存在，也可能仍在等待上游服务器。

更稳妥的做法是在启动脚本或应用入口增加有效性检查：

```bash
while ! date +%s | awk '$1 > 1700000000 { exit 0 } { exit 1 }'; do
  sleep 1
done

exec ros2 launch <package> <launch-file>
```

这里的阈值只是用来拒绝明显错误的年代，不用假装能验证绝对准确时间。生产环境还应检查同步状态，并设置等待超时和降级提示。

## 时间源要分清

墙上时钟会被校正，适合记录真实事件时间；单调时钟只向前走，更适合计算进程内部的持续时间。传感器若自带硬件时钟，还要处理它与主机时钟之间的偏移和漂移。

理想状态下，驱动层明确时间来源，算法层拒绝倒退、跳跃和超出合理范围的时间差，而不是把任何时间戳都当作可信输入。

## 修好跳变以后继续排查

消除时间跃迁后，轨迹仍可能缓慢漂移。这时才应继续检查场景几何退化、IMU 标定、雷达—IMU 外参、振动和计算延迟。不要把两个问题混成一个，也不要因为解决了最醒目的故障就提前结束验证。

这次经历让我把时间看成了系统中的另一种传感器：它有来源、精度、同步状态和失效模式。更多无人机排错方法整理在[从黑屏到数据链路的调试工具箱](/drone/debug-toolkit/)中。
